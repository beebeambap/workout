§ 01 — Executive Summary

5개의 결정적 발견

심각도 순서가 아닌 v1 사양에서 가장 먼저 흔들리는 가정부터 정렬했다.

F·01

localStorage 5MB 가정은 90일 안에 깨진다

이미지 base64는 33% 오버헤드. 800px·JPEG 0.85로 약 60–120KB/장 → 동작 60–80개 등록 시점에 한계. 시드 캐시까지 같은 도메인에서 경쟁한다. IndexedDB + Blob은 v1 직후 작업이어야 한다.

HIGH
F·02

「sets × reps」 만으로는 운동을 기록할 수 없다

중량·시간·거리·RPE·세트별 변동이 빠져 있어 사용자는 결국 memo 필드에 자유 텍스트로 떠넘긴다. 그러면 §8 진척도·PR·검색 기반이 모두 무너진다.

HIGH
F·03

저장은 있는데 「돌아볼 이유」가 없다

history는 카드 리스트뿐. 주 단위 볼륨·연속 기록·PR 알림·근육군 밸런스가 없으면 3주 차 이탈률이 가장 큰 리스크가 된다. 출력(JPG)은 결과물이지 동기가 아니다.

HIGH
F·04

720px 고정 시트는 모바일에서 가로 스크롤을 강제한다

설계서가 명시한 절충(§5)이지만, 「JPG로 저장 후 본다」는 우회는 일상 사용을 매번 두 단계로 만든다. 반응형 시트 + 별도 export 시 1440px 렌더로 분리해야 한다.

MID
F·05

1,324개 시드, 한국어 0개

§9에 후속 과제로만 적혀있지만 실제 검색 사용성을 결정한다. 한국어 입력으로 「벤치」 → bench press 가 매칭되지 않으면 시드 자체가 발견되지 않는다.

MID
§ 02 — Current State Diagnosis

잘 한 것과,
가정이 흔들리는 곳.

강점 · WORKS

SCHEMA
v1 키 네이밍workout.exercises.v1 / workout.routines.v1 — 마이그레이션 경로 미리 확보. §8의 migrateRoutineItems() 도 모범 사례.
RESIZE
업로드 시 800px·0.85 인코딩localStorage 한계를 미리 인지하고 입력 시점에서 정규화. 흔한 실수를 피했다.
RESOLVE
resolveExercise(item) 추상화local/seed 양쪽을 표준 표시 객체로 평탄화 — 출처가 늘어나도 렌더 코드는 안정적.
EXPORT
단일 테이블 시트동작 카드를 분리하지 않고 한 표에 묶은 결정 — 인쇄·캡처에서 시각적 통일감이 강하다.
PIPE
이중 검색 풀 + 배지 구분local과 seed를 합치되 출처를 시각화 — 데이터 신뢰도 측면에서 옳은 방향.

가정 위험 · ASSUMPTIONS AT RISK

CAPACITY
「localStorage ~5MB」 가정iOS Safari는 도메인당 더 빡빡하고, 캐시 추출과 경쟁한다. base64 저장 자체가 비효율.
INPUT
sets/reps 두 필드중량·시간·거리·RPE·세트별 가변값이 모델에 없다. 자유 메모로 흘러간다.
OUTPUT
720px 고정 + JPG only모바일 가로 스크롤. PDF 다중 페이지·9:16 공유·인쇄 A4 배치 부재.
ANALYTICS
history = 리스트주간 볼륨·근육군 밸런스·연속 기록·PR 추적이 데이터 모델 차원에서 불가능에 가깝다.
SEED
3.5MB JSON + 외부 이미지 핫링크첫 로드 트래픽 + raw.githubusercontent.com 가용성·CORS 의존. 오프라인 시 시드 깨짐.
i18n
한국어 매핑 없음검색이 영어 토큰에서만 동작 — 시드 1,324개의 가치를 70%+ 손실.
DATA MODEL
B+
스키마 버전·마이그레이션은 모범. 입력 다양성에서 감점.
UX FLOW
B−
탭 3개로 명확. quick-log·반복 루틴·즉시 시작 부재.
OUTPUT
C+
JPG 단일 포맷, 720px 고정. 공유 시나리오 미흡.
RETENTION
D
동기 부여 장치 없음 — 가장 큰 v2 기회 영역.

01

데이터 / 스토리지

IndexedDB Blob Backup Schema v2
IMPACT 운영 안정성의 천장을 올린다 EFFORT M · 1주 (마이그레이션 포함) RISK 구버전 유저 데이터 손실 가능 → 자동 백업 필수

localStorage 의 천장을 IndexedDB 로 들어올린다

v1 의 마이그레이션 패턴(migrateRoutineItems)을 그대로 재사용해 v2 스키마로 끌어올린다.

현재

  • 이미지 = base64 문자열, 33% 오버헤드
  • 모든 데이터가 5MB localStorage 한 통 안에서 경쟁
  • 백업/복원 = JPG 캡처가 유일
  • 스키마 변경 = 즉시 마이그레이션 1회, 롤백 불가

제안

  • 이미지/GIF 는 IndexedDB blob store 로 분리
  • 메타(exercises/routines) 만 localStorage 유지 → 빠른 첫 페인트
  • JSON 백업 export/import (수동 동기화 대용)
  • 스키마는 {version, migrate(prev)} 체인으로 누적
// schema v2 — split heavy from hot const stores = { 'wo.meta.v2': { exercises: ExerciseMeta[], routines: Routine[] }, // localStorage 'wo.media.v2': { [exerciseId]: Blob }, // IndexedDB 'wo.cache.v2': { seed: SeedIndex, ttl: number } // IndexedDB }; + exportBackup(): { meta, mediaManifest, version } → JSON.gz + importBackup(file): validate → diff → apply

현재 — 3가지 시각 문법

  • 라이브러리: 카드 그리드 (이미지 위, 이름 아래)
  • 루틴 빌더: 항목 + 드롭다운 (테이블도 카드도 아님)
  • 시트: 좁은 표 (1줄 row)
  • 같은 운동이 화면마다 다르게 「보임」

제안 — 1 primitive · 3 variant

  • 전 화면이 같은 ExerciseRow 만 사용
  • density 변수만 바꿈 → 학습 비용 0
  • 시트도 같은 컴포넌트의 compact variant
  • 썸네일/메타/배지 위치가 모든 화면에서 일관

§ 06 — Open Questions / Risks

결정해야 할 것들.

시드 데이터 라이선스

hasaneyldrm/exercises-dataset 는 비상업 한정. 상업화 시점에 ExerciseDB Pro / wger-data 검토. 그 전까지 「출처 명시 + 비상업」 워터마크를 시드 항목 카드 하단에 노출할지?

시드 이미지 핫링크

raw.githubusercontent.com 가용성에 의존. CORS·rate-limit 발생 시 사용자 경험이 즉시 무너진다. 미러링 (Cloudflare R2 / 무료 IPFS) vs 「내 라이브러리 우선」 정책 강화 중 선택 필요.

「간단 모드」 보존

중량·RPE 도입은 헬스 사용자에는 필수, 홈트 사용자에는 과잉. 기본은 reps 만 표시, 「상세 입력」 토글로 weight/RPE 펼침 — 이 토글의 디폴트를 사용자 첫 운동 분류에서 추론할지?

단일 HTML 의 한계선

대시보드·차트가 들어가면 인라인 JS 가 ~80KB 를 초과한다. Phase 03 시점에 「단일 HTML」 원칙을 유지할지, 「폴더 단위 정적 사이트」로 완화할지 결정해야 함.
